# File Extensions

# 1. The biggest thing I learned: XRD data is not just one type of file

This is probably the most useful domain point for your discussion.

For example, **Match!** supports a very large number of manufacturer-specific raw-data formats, including:

* Bruker/Siemens `.raw`
* Bruker `.brml`
* PANalytical `.xrdml`
* Rigaku `.ras` / `.raw`
* Siemens `.uxd`
* STOE `.raw`
* JEOL `.txt`
* Generic ASCII `.dat`
* Generic 2-column profiles
* Peak-list files such as `.pks` and `.dif`

Match! can also import **more than one diffraction pattern** and can automatically identify supported formats. ([crystalimpact.com][1])

That is interesting for FC Cubic because it shows that **file extension alone doesn't necessarily tell you the scientific role of a file**.

For example, Match! explicitly supports `.dat` in multiple contexts. `.dat` can represent different kinds of profile data depending on its internal structure. ([crystalimpact.com][1])

### This supports your earlier question

You were asking:

> Does `.dat` mean Raw or Preprocessed?

The answer from the domain is basically **not necessarily**.

You cannot safely determine the scientific role purely from the extension.

# 2. GSAS-II is especially relevant to FC Cubic

GSAS-II's import workflow is also interesting.

Its documentation describes importing **one or more 2D powder diffraction images**, and it supports many image formats, including detector formats such as MAR345, ADSC and TIFF. It also notes that important experimental information such as wavelength may be stored separately as metadata, because image acquisition software does not always populate those fields correctly. ([Advanced Photon Source][2])

This is a very important concept:

> **The data file and its metadata may be separate things.**

That aligns nicely with your FC Cubic requirement around:

`metadata.all.json`

and metadata extraction.

So tomorrow, if metadata comes up, you can say something like:

> **“I noticed from looking at GSAS-II that experimental information such as wavelength may not always be reliably contained in the primary measurement file, and metadata can sometimes be provided separately. So I wanted to understand whether FC Cubic considers the measurement file and metadata as separate but related upload artifacts.”**

That sounds much more domain-aware than simply asking "what metadata do we need?"

# 3. GSAS-II also shows that images can be legitimate crystallography input

This connects directly to your opinion about `.png`.

But there is an important distinction.

GSAS-II supports **scientific diffraction images** from detectors. Its documentation specifically discusses image import and formats such as TIFF, MAR345 and ADSC. ([Advanced Photon Source][2])

That does **not** mean an ordinary `.png` screenshot of an XRD graph is equivalent to raw diffraction data.

So there are really two concepts:

**Scientific measurement image**

```text
Detector → image data → analysis
```

versus

**Reference image**

```text
Screenshot / plot / photograph → information for scientist
```

That distinction could become useful in FC Cubic.

You can say:

> **“I came across the distinction between scientific detector images and ordinary reference images. So I wanted to clarify whether FC Cubic's upload layer is intended to preserve both analysis data and supporting/reference files, even if the latter cannot be directly consumed by an analysis engine.”**

That is a very good client question.

# 4. Match! gives you another interesting insight: missing metadata can be entered manually

Match! says that if an imported diffraction data file doesn't contain all the information required—for example, **wavelength**—the user is asked to provide the missing experimental details manually. ([crystalimpact.com][3])

This maps extremely well to your FC Cubic requirement:

```text
Metadata available?
       |
    YES → extract metadata
       |
     NO
       ↓
Manual composition / information
```

So your flow isn't unreasonable from a domain perspective.

But you may want to clarify whether FC Cubic will eventually have a broader **manual experimental-details fallback**, rather than only manual composition.

# 5. Raw vs processed data is more complicated than the extension

This is probably the **most valuable thing for your PM discussion**.

Match! itself distinguishes between experimental/raw profile data and calculated profile data. It can export both experimental profile data and calculated profile data, sometimes using the **same `.dat` extension**. ([crystalimpact.com][4])

So:

```text
.dat
```

doesn't inherently mean:

```text
Raw
```

or

```text
Preprocessed
```

The **content and provenance** matter.

That's strong evidence for your question to Amrinder:

> “For `.xy`, `.csv`, `.dat`, `.txt`, and `.fxye`, are these extensions simply identifying the file as an XRD Pattern, with Raw vs Preprocessed being a separate classification?”

I would **keep this question in your client-call list**.

# 7. CIF is different from ordinary pattern data

The IUCr describes CIF as a standard for **exchange and archiving of crystallographic information**. It isn't simply another XRD pattern file. ([International Union of Crystallography][6])

And CIF can contain much more than just a unit cell.

For example, crystallographic structure information can include:

* unit-cell parameters
* symmetry
* atom-site information
* experimental information
* refinement information
* metadata

The IUCr also provides validation infrastructure around CIF. ([International Union of Crystallography][6])

So your FC Cubic decision to treat:

```text
.cif → CIF / Phase
```

as a separate category makes **good domain sense**.

# 8. Your "upload everything associated with the sample" idea is actually interesting

After looking at these tools, I think your opinion has **some good domain justification**, with one caveat.

A scientist's working directory can contain many different artifacts:

```text
Sample/
│
├── Raw measurement
├── Converted pattern
├── Processed pattern
├── CIF
├── Instrument parameters
├── Refinement project
├── Metadata
├── Detector image
├── Previous refinement
├── Calculated pattern
└── Reports / plots
```

Established tools also deal with multiple data formats, metadata, experimental details, calculated patterns, peak data, etc. ([crystalimpact.com][1])

So your thought:

> **"Let the scientist upload the files associated with the sample and decide later which ones are useful for analysis."**

is **not a strange idea from a scientific workflow perspective**.

The important distinction is:

**Storage/repository ≠ analysis input.**

A file can be worth preserving even if the current analysis engine cannot use it.
